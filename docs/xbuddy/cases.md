## 案例 1 · 两个意图只答一个，第 4 条引用永远用不上

**现象**　问「保修期多久？换货要什么条件？」这类含两个意图的问题，回答只覆盖前半段；引用面板固定给 4 条，但第 4 条从未被正文引用过。

**根因**　两处叠加：`apply_filter` 按**总分**统一截断（Top-K 只看整体相似度，不看它服务哪个问句），`_generate_mock` 又只取前 3 块拼答案。两个意图争抢同一个候选池，后一个自然被挤掉。

**AI 当时的做法**　按契约实现检索链路：召回 → 阈值过滤 → 取 Top-K → 生成。每一步单看都对，**错在把"多意图"当成"单意图的多次调用"**。

**我怎么发现的**　D5 验收时拿回答对照 `docs/demo-script.md` 的预期，发现只覆盖了前半段；再把引用逐条回填到正文，发现第 4 条悬空。

**修正**　① 过滤阶段按问句分段保底：每个子问句至少留 1 块，再按分数补足；② 引用编号按"首次被正文引用"的顺序单调分配，没用到的候选不编号。

**回归证据**　`pnpm test:rag` 新增 4 条（多意图保底、引用编号单调、阈值边界、表格块重复表头）；`pnpm eval:rag` 36 条未退化（hit@4 1.0 / 边界 97.2%）；`node scripts/e2e.mjs` D5 稳定带 4 条引用。

**教训**　"检索质量"指标全绿也可能答不全——**命中率衡量的是找到没有，不是答全没有**。评测集必须含多意图样本。

## 案例 2 · 幂等键交给模型生成，重放一次就换新 uuid

**现象**　D4「帮我建个工单」连点两次，本该去重，实际建出两张单。

**根因**　契约里 `create_ticket` 的入参含 `idempotency_key`，由模型填。模型每轮都会重新生成一个 uuid，**同一个语义请求在系统看来是两个不同请求**。

**AI 当时的做法**　照抄文档的字段定义，把 key 当普通参数透传；甚至在 schema 里给它写了 `description: "唯一标识，用于幂等"`。

**我怎么发现的**　D4 连点两次做验收，第二次返回的是新单号而不是 `deduplicated: true`；对比两次请求的参数，`idempotency_key` 不一样。

**修正**　① 从模型可见的 schema 里**删掉**该字段（传了会被 strict schema 拒绝）；② 由网关按 `会话 + 订单号 + 工单类别 + 摘要指纹` 派生，模型完全不可见；③ 摘要指纹而不是只看类别——否则「少发」和「破损」会被折叠成同一张单。

**回归证据**　`tools.test.ts` 覆盖"幂等键派生"与"模型传该字段被拒"；E2E D4 二次 `deduplicated: true`；`domain.test.ts` 覆盖摘要相似度 ≥0.7 才判重、未关闭工单上限 3 张。

**教训**　**凡是"系统不变量"，都不能交给概率模型维护**。身份、幂等、权限这类字段，模型看得见就等于可以被它改写。

## 案例 3 · 上游 SSE 遇 CRLF 分帧，整条流静默丢失

**现象**　切到真实模型后偶尔"一个字都不出"，但 HTTP 200、无报错、前端也不卡。

**根因**　手写的流式解析按 `\n\n` 切事件。OpenAI 兼容实现里有用 `\r\n\r\n` 分帧的，切不出来就一个事件都解析不到，循环安静地跑完。

**AI 当时的做法**　按最常见的 `data: ...\n\n` 写了解析器，并用同一种格式造了测试数据——**用自己的假设验证自己的实现**。

**我怎么发现的**　真实模型演练（`pnpm drill:model`）里文本流式拿不到首 token；把响应体按原始字节看，分帧是 `\r\n\r\n`。

**修正**　分帧改为宽松匹配（同时接受 `\n` / `\r\n`，允许跨 chunk 截断与粘包），并在 chunk 边界处保留残余缓冲。

**回归证据**　`providers.test.ts` 5 条：CRLF 分帧、跨 chunk 逐字节切碎（含多字节汉字）、粘包、截断 flush、`tool_calls` 增量累积。`sse.test.ts` 另有 4 条覆盖网关侧的同类问题。

**教训**　**解析器的测试数据不能由实现自己生成**，否则只能证明"我按我的假设写对了"。这类 bug 只在真上游暴露，所以换模型前必须先跑演练。

## 案例 4 · 正常作答被标成 `tool_limit`

**现象**　界面上正常的回答偶尔挂一条"工具调用次数超限"的提示，但工具明明只调了一次。

**根因**　用"本轮是否还有 tool_call 意图"来判断是否超限，而模型在**最后一轮**常常带着一个"我想再查一下"的念头直接作答。判定写在了生成之前，于是把正常收尾标成了超限。

**AI 当时的做法**　在编排循环出口统一判定 `finish_reason`，条件写成"本轮请求了工具但没执行"。

**我怎么发现的**　trace 里出现自相矛盾的组合：只有「1 个步骤」，却标着 `tool_limit`。

**修正**　出口判定区分两种情形：末轮**已产出正文** → `stop`；只有"还需要工具但预算用尽"才标 `tool_limit`。

**回归证据**　`orchestrator.test.ts` 5 条：末轮作答不误标、预算用尽仍要工具才标、`enable_knowledge` 关闭时不触达下游、不误发 handoff。

**教训**　状态机的"出口条件"最容易写成"看起来对"——**要用反例测**（正常收尾 / 超限 / 被拦截），不能只测 happy path。

## 案例 5 · direct 链路被熔断器一起掐断，双链路对比当场翻车

**现象**　演示 D8 时，proxy 链路熔断后切到 direct，direct 也一起不可用——本想展示"降级"，结果展示成"全挂"。

**根因**　熔断器状态挂在 provider 实例上，两条链路共用同一个实例。

**AI 当时的做法**　"熔断属于 provider 的能力"这个直觉很自然，实现也就顺手挂在了 provider 上。

**我怎么发现的**　`chain.test.ts` 里「熔断后 direct 仍可调用」这条期望一开始是红的——先写期望再实现，比先实现再补测试更容易发现串味。

**修正**　熔断器按链路隔离：proxy 有独立状态，direct 不经过熔断判断（它本来就是"单次透传、不重试不降级"的语义）。

**回归证据**　`chain.test.ts` 6 条：direct 不重试、proxy 退避、不可重试错误、降级、熔断、熔断后 direct 仍可调用。

**教训**　**"能力挂在谁身上"决定故障的传播范围**。挂在共享实例上，一次故障就会同时打穿两条链路。

## 案例 6 · 文档写 `text-embedding-3-small`，代码其实是内置 hash

**现象**　manifest 与文档声称用了 OpenAI 的 embedding 模型，实际跑的是自己写的 n-gram hash。

**根因**　为了离线可复现先上了 hash 兜底，文档沿用了"规划里要用的模型"，**规划与实现没对齐**。

**AI 当时的做法**　代码里老实写着 `hash`，文档里照着路线文档抄了 `text-embedding-3-small`——两边都"没错"，合起来是错的。

**我怎么发现的**　自检时把 `/health` 的 `embedding` 字段和 manifest 里的 `provider` 对了一遍，发现对不上。

**修正**　不遮掩，改成如实标注：`/health` 明示 `hash:hash-ngram-512:512`；文档写清默认 hash、怎么切 bge（`EMBEDDING_PROVIDER=bge`，且**必须重建索引**，签名变了）；理由写进 ADR-007（现场网络与 torch 体积风险）。

**回归证据**　`curl :8083/health` 的 `embedding` 字段；`docs/knowledge-base.md` 与 ADR-007 口径一致；README §8 已知限制第 1 条。

**教训**　**降级可以，装作没降级不行**。评委不会因为用 hash 扣分，但会因为"文档和实现对不上"扣分。

## 案例 7 · 契约改了 `shared` 忘记导出，CI 必红

**现象**　`packages/shared` 的 `SSE_EVENT_NAMES` 有 10 类事件，`contracts/sse-events.json` 只有 9 类（少了 `reasoning`）。

**根因**　事件是后加的，改完 TS 侧就继续做功能，**没重跑导出脚本**。契约的"单一真源"只真了一半。

**AI 当时的做法**　加事件、改前端、跑单测——单测全绿，因为单测直接从 `shared` 导入，根本不看导出物。

**我怎么发现的**　交付自检时拿 README §1 的"10 类事件"去对 `contracts/sse-events.json`，数出来 9 个；顺带发现 README §2 架构图还写着"9 事件"，两处自相矛盾。

**修正**　重跑 `pnpm contracts` 补齐 `reasoning`；README 口径统一为 10 类。CI 里本来就有"导出后 `git status --porcelain contracts/` 必须为空"的检查，这次是真的会红。

**回归证据**　连续两次导出 md5 相同（幂等）；CI 的 Node job 该步骤通过；`test_contract.py` 在 Python 侧按同一份 JSON Schema 做实例校验。

**教训**　**"单一真源"必须配一条会失败的检查**，否则真源只是"主要来源"。凡是生成物，都要有幂等性验证。

## 案例 8 · 文档里的测试命令想当然，照抄直接 ImportError

**现象**　README 与 `docs/testing.md` 都写 `cd services/rag && python -m unittest discover -s tests`，照抄执行报 `ModuleNotFoundError: No module named 'pydantic'`，`Ran 17 tests, FAILED (errors=2)`。

**根因**　依赖装在 `services/rag/.pylibs`（`pip install --target` 的目录，不进 `sys.path`），文档写命令时按"标准 venv 直觉"写的，**没在这台机器上照抄跑过一遍**。

**AI 当时的做法**　写文档时顺手补了一条"看起来合理"的命令；它自己跑测试时用的是 `PYTHONPATH=.pylibs` 前缀，两套命令不一致。

**我怎么发现的**　交付前按 README 从零走验收路径，第一条就挂。

**修正**　新增 `pnpm test:rag`（`scripts/run-rag-tests.mjs`）：自动探测 `.venv` / `.pylibs` / `RAG_PYTHON`，注入 `PYTHONPATH` 后再跑 unittest。顺带解决 Windows 的 cmd / PowerShell 不支持 `VAR=x cmd` 前缀语法的问题。README 与 `docs/testing.md` 同步换成这条命令。

**回归证据**　`pnpm test:rag` → `Ran 26 tests ... OK`；CI 的 Python job（干净 runner，依赖装在 site-packages）同样通过，证明两条路径都成立。

**教训**　**文档里的命令必须照抄跑一遍**。写的人和验的人如果是同一个 AI，它会不自觉地用"自己知道的那条命令"，而不是"文档里写的那条"。
