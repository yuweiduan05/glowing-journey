# XBuddy 使用记录 · 知言

> 本目录归档「AI 编程助手参与本项目」的过程证据，对应评分表里 **AI 工具使用（20%）** 一项。
> 收录口径不是"我用了 AI"，而是 **"AI 生成了什么 → 我怎么验的 → 验出什么问题 → 怎么改的 → 拿什么证明改对了"**。

---

## 1. 工具与形态

| 项 | 情况 |
| --- | --- |
| 工具 | AI 编程助手（WorkBuddy 桌面端：对话式改码 + 本地命令执行 + 浏览器验证）。目录名沿用课程资料里的「XBuddy」口径 |
| 使用方式 | 我提目标与约束 → 助手读仓库、写代码、跑命令 → 我看结果、否掉不合适的方案 → 它改 → 跑验收 |
| 介入深度 | 单轮改动能小到一处样式、大到整个 RAG 状态图；但**每一轮的验收命令都由我先定**，助手不许自证"我改好了" |
| 未使用 | 没有让 AI 直接生成整包后照抄；没有用 AI 生成"看起来能跑"的假数据糊弄演示 |

## 2. 我给自己定的四条协作规矩

这四条是这三周反复踩坑后定下来的，也是本归档的主线：

1. **先要验收命令，再要代码。** 每轮开始先说清"用什么命令证明它对"（`pnpm test` / `pnpm eval:rag` / `e2e.mjs` / `/health`），没有验收标准的改动不接。
2. **模型说的数字必须能复现。** AI 说"评测 97.2%"这类话一律不信，自己跑一遍 `pnpm eval:rag` 看输出；跑不出来就写"未验证"。
3. **不确定就查，不许猜。** 猜 API 行为、猜端口、猜契约字段，是这类项目里最容易埋雷的地方（见案例 3、6）。
4. **每轮收尾必须留痕。** 改了哪个文件、为什么改、验没验，写进当日工作日志；否则第二天连自己都记不清。

## 6. 三点如实说明

1. **对话原文没有逐条留存。** 桌面端助手没有导出对话的功能，本归档依据的是当天写下的工作日志、代码审查报告、git 提交与 CI 记录——属于**事后复盘**，不是聊天记录转贴。
2. **开发节奏不均匀。** 10-22 是集中攻坚（一天把七个模块立起来），之后是分阶段的整改与打磨；不是每天平均推进。归档按阶段而不是按"第 N 天"组织，就是为了不制造这种假象。
3. **AI 出的错比这里写的多。** 只收录了有明确回归证据、能复述清楚的；剩下的是"改完就过、没留痕"的小来回，写进来反而不可信。
